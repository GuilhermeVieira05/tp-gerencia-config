4:00–5:30

Pipeline de implantação

Push na main e PR: Commit + Aceitação. Tag vX.Y.Z: as três etapas. A imagem Docker é construída uma só vez.

1. Commitnpm ci · build · testes de unidade · testes de integração (117 + 55). O tsc aqui valida a compilação
▶
2. Aceitaçãoconstrói a imagem · sobe o contêiner · 22 testes caixa-preta via HTTP · salva a imagem
▶
3. Lançamento(só em tag) carrega a mesma imagem, confere o ID · GHCR · Release · deploy.sh · /health com a versão
  • needs entre as etapas: falha em uma bloqueia as seguintes
  • Segredos só no environment production; nenhum no repositório
  • Entrega contínua: a tag é a decisão humana de liberar (baseline). Implantação contínua (deploy a cada merge) não adotamos
  • Artefato: a imagem testada na Aceitação é a publicada; o ID é conferido antes

8:50–9:40

Lições aprendidas

Re-run quebrava o Lançamento.

A tag v0.1.0 falhou: o step de Release retornou HTTP 422 porque o Release já existia. → Tornamos o step idempotente (PR #3). → Testaríamos o re-run antes de criar a primeira tag.

Imagem testada ≠ imagem publicada.

Construíamos a imagem 3 vezes. → Agora é 1 build, salvo como artefato; o Lançamento confere o ID. → Teríamos desenhado o artefato único desde o início.

Plano e prática divergiram.

O plano descrevia main protegida e revisão de PR que o GitHub não aplicava. → A auditoria cruzou plano × repositório; o plano agora separa o definido do praticado. → Ativaríamos a proteção e as reviews no primeiro dia, com issues desde o PR #1.

Dependência entre pessoas.

A Aceitação só passava com as rotas HTTP prontas. → Fixamos a tabela de rotas como contrato. → Acordaríamos o contrato antes de dividir o trabalho.
